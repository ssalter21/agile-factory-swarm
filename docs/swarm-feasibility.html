Feasibility & build sizing

Rebuilding swarm-forge inside the agent harness

Can Uncle Bob's tmux swarm be rebuilt as sub-agents and harness orchestration — with a spec swarm, a human approval seam, and a web front end — on Claude and Copilot, without cloud sandboxes?

Prepared 19 Aug 2026 Target agile-factory-swarm Host Windows 11 · local-first

Yes — and most of swarm-forge is now redundant. Nearly every mechanism Uncle Bob hand-built in Babashka and tmux (role prompts, worktree-per-agent, a handoff daemon, a terminal window per role, a layered constitution) ships natively in Claude Code today as subagents, agent teams, dynamic workflows, worktree isolation, and hooks. Porting means deleting infrastructure, not writing it.

The three things you actually have to build are: the spec swarm and its approval seam (a config format plus two orchestration scripts), the web front end (an event sink fed by HTTP hooks plus a transcript reader), and the vendor adapter if you genuinely want the same swarm running on Copilot.

A config-only version that works at your desk and drops into a work repo is two to four evenings. The version with your own web UI, live from anywhere, is six to ten weeks of side-project time. Nothing in the vision is blocked — but two constraints shape the build, and both are in §7.

01What swarm-forge is, mechanically

Strip the philosophy and swarm-forge is five moving parts: a swarmforge.conf declaring a topology of named roles; a .prompt file per role; a layered "constitution" of shared engineering articles that local files can override; a git worktree per role so agents never collide; and a handoff protocol — swarm_handoff.sh, ready_for_next.sh, done_with_current.sh feeding a Babashka daemon — that queues validated messages between roles. tmux gives each agent a visible window; the branch you check out (two-pack, four-pack, six-pack) picks the team.

The insight worth keeping is the topology: specifier → coder → cleaner → architect → hardener → QA, each with a narrow remit and a validated handoff rather than a shared chat. The implementation is a workaround for capabilities that didn't exist when it was written. It also assumes zsh, tmux and Babashka, which on Windows means WSL — a second reason to rebuild rather than port.

Where the parity breaks

Copilot has custom agents, subagents with isolated context, and /fleet for parallel fan-out — enough to run the builder swarm. It has no documented equivalent of hooks-to-HTTP, worktree isolation as config, peer-to-peer agent messaging, or a workflow scripting layer. Treat Copilot as a degraded execution target, not a co-equal one, and design accordingly (§6).

03Three tiers, and what each one costs you

These are a genuine escalation: each tier is the previous one plus a layer. You can stop at any of them and have something that works.

A

Config only

2–4 evenings

A .claude/ directory and nothing else. Roles as subagent files, constitution as CLAUDE.md and rules, two saved workflows (/spec-swarm, /build-swarm), a blackboard directory in the repo.

You get

  • Full builder swarm with worktree isolation
  • Spec swarm with a real approval gate
  • Live monitoring via /workflows and /tasks — drill into any agent's prompt, tool calls and result
  • Jump into a running agent and steer it (SendMessage, or Enter on its panel row)
  • Remote access via Remote Control, from browser or phone
  • Drops into a work repo as a skill with zero infrastructure

You don't get

  • Your own UI, your own data model, or history that outlives the session
  • A cross-project swarm dashboard
B

Local orchestrator + web UI

4–7 weeks

A small TypeScript service on your machine: the Agent SDK drives the swarm, an HTTP hook endpoint receives every lifecycle event, SQLite stores runs, a React app streams it over WebSocket.

Adds

  • Swarm graph, per-agent transcript panes, shared-context viewer
  • Persistent history across sessions and projects
  • Approval gates as a real UI action, not a terminal keypress
  • Personality configuration as data, not markdown files
  • Reachable from anywhere over a Tailscale or Cloudflare tunnel

You don't get

  • Copilot as a backend
  • Agents that outlive the orchestrator process
C

Multi-CLI supervisor

+3–4 weeks

Roles become processes behind an adapter. Each backend — claude -p --output-format stream-json, copilot -p, others — is normalised into one event envelope. A worktree pool and durable queue sit underneath.

Adds

  • True vendor portability; mix backends inside one swarm
  • Long-running agents that survive a restart
  • Runs on your existing CLI login rather than metered API keys
  • tmux attach as a debugging escape hatch

Cost

  • You rebuild the process supervision swarm-forge exists to provide — pty handling, crash recovery, zombie reaping

04The spec swarm and the seam

This is the part with no off-the-shelf answer, and the part most worth getting right. The requirement: a short human input, several configured personalities shaping it, and a reviewable artifact that becomes a contract for the builder swarm.

The critical design constraint comes from the runtime: a dynamic workflow cannot take user input mid-run. Only permission prompts pause it. So the approval seam is not a step inside one swarm — it is the boundary between two separately-invoked workflows. That constraint is a gift; it forces the artifact to be real.

The artifact is the seam

Write it to specs/<slug>/ in the repo: spec.md, acceptance.feature, tasks.md, non-goals.md, open-questions.md. Files, not a database — they diff in git, they survive every tier of this build, and every vendor's agent can read them. This same directory doubles as the shared context your front end renders. It replaces swarm-forge's handoff queue entirely: agents read and write the blackboard, and the queue is just file state.

Make one rule non-negotiable: the builder swarm's first action is to restate the spec as it understands it and fail loudly on any gap. Spec drift is the failure mode that kills multi-agent pipelines, and it is cheap to catch at the seam and expensive to catch at QA.

05Tracking agents and the web front end

You have four independent sources of truth, and a good UI uses three of them:

  • HTTP hooks — the backbone. A hook entry of type: "http" POSTs the event JSON to a URL you choose, carrying session_id, agent_id, agent_type, transcript_path, tool name and tool input. Register SubagentStart, SubagentStop, PreToolUse, PostToolUse, TaskCreated, TaskCompleted and SessionEnd and you have a complete live event stream into your own server without touching the SDK. Mark them async: true so they never block an agent.
  • Session transcripts — JSONL under ~/.claude/projects/<encoded-cwd>/, one file per session, with subagent transcripts stored separately. The SDK exposes listSessions() and getSessionMessages(), so "jump into this agent's conversation" is a file read, not a protocol.
  • The SDK message stream — if the orchestrator itself calls query(), every assistant message, tool call and result arrives as an async iterable. Messages from inside a subagent carry parent_tool_use_id, which is how you build the tree view.
  • The blackboard directory — file-watch specs/ and .swarm/ and render it. This is your shared-context pane, and it's ten lines of code.

Writing back into a running agent is the one asymmetry. From the terminal it's the agent panel or SendMessage. From your own UI at Tier B you hold the SDK session and resume it by ID; at Tier C you write to the process's stdin. Both work; neither is free.

For "accessible from anywhere" before you've built anything: Remote Control already does it. It's a research preview that connects claude.ai/code or the mobile app to a session running on your machine, with subagent and workflow progress synced across every connected device and execution staying local. That covers the requirement at Tier A for zero build cost — and stays useful as a fallback after your own UI exists.

06Running the same swarm on both vendors

Don't write role definitions twice, and don't write to the lowest common denominator. Keep one neutral source — a swarm/ directory of YAML role definitions plus prompt bodies — and compile it:

  • swarm/roles/*.yaml → .claude/agents/*.md (full fidelity: tools, model, worktree isolation, permission mode, memory)
  • swarm/roles/*.yaml → .github/agents/*.agent.md (degraded: name, description, instructions, tools)
  • swarm/constitution/*.md → CLAUDE.md and AGENTS.md

Orchestration can't be compiled the same way — Claude gets a dynamic workflow script, Copilot gets a shell script driving /fleet and sequential invocations. Accept that divergence; it's roughly 200 lines each. The compiler itself is an afternoon, and it's what makes the "drop this into a work repo" story real: whichever tool your employer allows, the roles are identical.

Recommended sequence

  1. Build Tier A completely first, and use it on a real side project. It's cheap, it's the thing you can take to work, and it will change your role definitions more than any amount of up-front design will.
  2. Add the hook event sink alone — no UI, just a server writing events to SQLite. You get persistent history immediately, and it proves the observability model before you spend two weeks on React.
  3. Settle the auth question, then build the orchestrator on whichever process model that answer implies.
  4. Web UI read-only, then interactive. Watching a swarm is 80% of the value and 30% of the work.
  5. Copilot backend last, if at all. The compiler from step 1 already gives you portable roles; a second execution backend is the most expensive item on this list for the least novel capability.
